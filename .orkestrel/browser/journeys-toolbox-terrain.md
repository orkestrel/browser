# Toolbox terrain for the journeys design (orkestrel/toolbox at 8976582, read 2026-09-30)

This note condenses four reader passes over the `orkestrel/toolbox` clone. It covers the stores, the database layer, the tools and their Model Context Protocol (MCP) surface, and the record of what worked. Every fact about toolbox carries a citation in the form (absolute path:line).

## 1. What toolbox is

`@orkestrel/toolbox` at version 0.0.16 supplies concrete tools that a large language model (LLM) can call: workflow authoring, workspace editing, sub-agent delegation, terminal-mediated prompting, database and relation access, schema inference, and endpoint wrapping, "with pluggable stores" (/home/user/orkestrel/toolbox/package.json:3, /home/user/orkestrel/toolbox/README.md:3, /home/user/orkestrel/toolbox/guides/toolbox.md:3). Each tool is a factory that returns a plain `ToolInterface` value, and the runtime envelope, the `ToolManager` registry, and MCP publication belong to `@orkestrel/tool` and `@orkestrel/mcp` (/home/user/orkestrel/toolbox/README.md:5, /home/user/orkestrel/toolbox/guides/toolbox.md:318, /home/user/orkestrel/toolbox/guides/tool.md:484). The clone is a single-commit shallow snapshot ("Overwrite with scaffold 0.0.81") with no changelog, so its history survives only in the guide, a three-item roadmap, source comments, and test titles (/home/user/orkestrel/toolbox/ROADMAP.md:1-3, /home/user/orkestrel/toolbox/AGENTS.md:1).

## 2. The store contract

### Interface and identity

The only store seam is the `DefinitionStoreInterface` interface, with three async methods: `get(id)`, `set(definition)`, and `delete(id)` (/home/user/orkestrel/toolbox/src/core/types.ts:509-519). Its doc comment names it the twin of the `TerminalStoreInterface` interface in `@orkestrel/terminal` (/home/user/orkestrel/toolbox/src/core/types.ts:509-511). The `set` method keys the entry by the definition's own `id` field and takes no separate id argument (/home/user/orkestrel/toolbox/src/core/types.ts:516-517). The stored entity is a config-only `DatabaseDefinition` record `{ id, driver, tables, primary?, indexes?, version? }`, never a live handle (/home/user/orkestrel/toolbox/src/core/types.ts:483-500, /home/user/orkestrel/toolbox/guides/toolbox.md:356).

### Revisions, listing, deletion, and ownership

- Revisions: no store carries an entry revision, etag, or compare-and-set; the `version` field is a schema target that a versioning driver stamps and reconciles, not a revision counter (/home/user/orkestrel/toolbox/src/core/types.ts:483-500, /home/user/orkestrel/toolbox/guides/toolbox.md:360).
- Listing: the interface has no list, page, or count method, so a consumer cannot enumerate stored definitions (/home/user/orkestrel/toolbox/src/core/types.ts:513-519).
- Deletion: a `delete` call for an absent id is a no-op that never throws (/home/user/orkestrel/toolbox/src/core/types.ts:518-519, /home/user/orkestrel/toolbox/src/core/stores/DatabaseDefinitionStore.ts:96-97).
- Ownership: the store owns only the blueprint and the driver owns the rows, and the `destroy` operation closes whatever handle is cached for the id, including one the embedder supplied (/home/user/orkestrel/toolbox/src/core/factories.ts:1108-1113, /home/user/orkestrel/toolbox/guides/toolbox.md:360).

### The two implementations

`MemoryDefinitionStore` is a private `Map` that applies `structuredClone` on both write and read, with no eviction and no time to live (/home/user/orkestrel/toolbox/src/core/stores/MemoryDefinitionStore.ts:13-27, /home/user/orkestrel/toolbox/src/core/stores/MemoryDefinitionStore.ts:40-73). `DatabaseDefinitionStore` holds one table named `definitions` with the columns `{ id: stringShape(), definition: rawShape({}) }`, so the whole definition is one opaque JSON column (/home/user/orkestrel/toolbox/src/core/factories.ts:1062-1071). Its `get` method narrows the stored blob through the `isDatabaseDefinition` guard and resolves `undefined` for a malformed blob (/home/user/orkestrel/toolbox/src/core/stores/DatabaseDefinitionStore.ts:71-77). Its `set` method is `table.set({ id, definition })` and its `delete` method is `table.remove(id)` (/home/user/orkestrel/toolbox/src/core/stores/DatabaseDefinitionStore.ts:86-97). The `createDatabaseDefinitionStore` factory defaults its driver to the memory driver, so the caller-supplied driver alone decides durability (/home/user/orkestrel/toolbox/src/core/factories.ts:1043-1045, /home/user/orkestrel/toolbox/src/core/factories.ts:1062-1071).

### The JSON store

Toolbox source and tests contain no JSON-file store, no `createJSONDriver` call, and no file path; comments only say a JSON, SQLite, or IndexedDB driver "swaps in" (/home/user/orkestrel/toolbox/src/core/stores/DatabaseDefinitionStore.ts:16-22, /home/user/orkestrel/toolbox/src/core/factories.ts:1150, /home/user/orkestrel/toolbox/src/core/types.ts:572-574). The JSON file behavior belongs to the `createJSONDriver` function of `@orkestrel/database/server`, documented in the vendored database guide mirror (/home/user/orkestrel/toolbox/guides/database.md:80, /home/user/orkestrel/toolbox/guides/database.md:950-954).

The mirror documents the following driver behavior; toolbox never exercises it.

- File layout: one JSON file per driver at the path the caller passes, holding `{ metadata?, tables }` (/home/user/orkestrel/toolbox/guides/database.md:80, /home/user/orkestrel/toolbox/guides/database.md:511-540).
- Atomicity: a flush writes a sibling temporary file and renames it onto the target path, and a native transaction clones the committed state into a candidate that one atomic file replacement publishes (/home/user/orkestrel/toolbox/guides/database.md:864, /home/user/orkestrel/toolbox/guides/database.md:511-516).
- Faults: a failing `mkdir`, `writeFile`, or `rename` call surfaces as a `DRIVER` database error after temporary-file cleanup (/home/user/orkestrel/toolbox/guides/database.md:532-536).
- Corruption: durable reads fail closed (/home/user/orkestrel/toolbox/guides/database.md:538).
- Containment: none of the four readers found a path containment check in toolbox or in the mirror sections they read; the driver takes the caller's path as given (/home/user/orkestrel/toolbox/guides/database.md:80).

### Concurrency and corruption at the store layer

The database tool assumes the single-writer, non-reentrant model of `@orkestrel/database` and does not serialize concurrent calls against one id (/home/user/orkestrel/toolbox/src/core/factories.ts:1112-1116). The `create` operation checks the cache and the store, awaits, and then writes, so its check-then-set is not atomic (/home/user/orkestrel/toolbox/src/core/factories.ts:1180-1221). At the store layer a malformed blob and a missing row look the same to the caller, and the guard rejects any blob carrying the superseded `keys` field instead of migrating it (/home/user/orkestrel/toolbox/src/core/validators.ts:106-108, /home/user/orkestrel/toolbox/tests/src/core/stores/DatabaseDefinitionStore.test.ts:136-148).

## 3. The database layer

The database layer in toolbox is one 121-line class, `DatabaseResolver`, that keeps a per-tool `Map` of live `DatabaseInterface` handles and, on a miss, reads the definition from the store, looks up the driver factory by name, builds the database with `createDatabase` over `expandTables`, and caches it (/home/user/orkestrel/toolbox/src/core/databases/DatabaseResolver.ts:93-120). An unknown id throws a `TOOL` error with the message `unknown database 'ID'`, where `ID` stands for the requested id (/home/user/orkestrel/toolbox/src/core/databases/DatabaseResolver.ts:119).

### What the database adds over a JSON store

A table is a contract: every write is validated against per-column shapes and every read is narrowed, a query engine runs conditions, order, limit, offset, count, and aggregate, point access takes one key or an array, and failures carry typed codes (`CONFLICT`, `VALIDATION`, `NOT_FOUND`, `ABORTED`, `MIGRATION`, `DRIVER`) (/home/user/orkestrel/toolbox/guides/database.md:9-18, /home/user/orkestrel/toolbox/guides/database.md:480-490). Neither the memory driver nor the JSON driver implements native queries, so every query scans in key order, and declared indexes take effect only on SQLite and IndexedDB (/home/user/orkestrel/toolbox/guides/database.md:507-511). Toolbox never calls `transaction`, `migrate`, `planMigration`, or `migrateRows` (/home/user/orkestrel/toolbox/src/core/factories.ts:1138-1324). The column DSL (domain-specific language) offers four primitives (string, integer, number, boolean) plus an optional flag, with no nested, array, JSON, or blob column (/home/user/orkestrel/toolbox/src/core/compilers.ts:26-64, /home/user/orkestrel/toolbox/guides/toolbox.md:348).

### How the two divide responsibilities

The definition store persists only the schema blueprint; the driver owns the rows, and a database re-minted over the default memory driver comes back empty (/home/user/orkestrel/toolbox/guides/toolbox.md:360, /home/user/orkestrel/toolbox/src/core/factories.ts:1108-1111). A second tool reads the first tool's rows only when both share one driver instance, which the re-mint test arranges on purpose (/home/user/orkestrel/toolbox/tests/src/core/factories.test.ts:2981-3007). Migration is creation-time only: a cached live database never evolves in place, and the tool description tells the model to open a freshly configured database over a versioned persistent driver (/home/user/orkestrel/toolbox/src/core/constants.ts:401, /home/user/orkestrel/toolbox/guides/toolbox.md:360).

### Keys and revisions

Each table keys rows by a primary column, `id` by default, overridable per table, and an omitted primary is filled by `crypto.randomUUID()` (a universally unique identifier) or by the configured generator that toolbox forwards to every database it mints (/home/user/orkestrel/toolbox/guides/database.md:737-741, /home/user/orkestrel/toolbox/src/core/types.ts:575-577, /home/user/orkestrel/toolbox/tests/src/core/factories.test.ts:2302-2324). Row writes use three verbs: `add` inserts and throws `CONFLICT` on a duplicate key, `set` upserts a whole row, and `update` patches an existing key and revalidates the merged row (/home/user/orkestrel/toolbox/src/core/factories.ts:1264-1296, /home/user/orkestrel/toolbox/tests/src/core/factories.test.ts:2591-2610). No row revision, etag, or updated-at column exists anywhere in toolbox (/home/user/orkestrel/toolbox/src/core/types.ts:483-500).

## 4. Tools over stores

### Declaration and parameters

Each tool is one `createTool` call with a name constant, a full description, a one-sentence summary, and parameters produced by `schemaToParameters(contract.schema)` from one compiled contract shape, so the advertised schema and the handler guard share one source (/home/user/orkestrel/toolbox/src/core/factories.ts:1138-1159, /home/user/orkestrel/toolbox/guides/toolbox.md:320). Multi-action tools (workspace, database, relation, answer) are one tool each, discriminated by an `operation` literal that leads every union arm, with `optionalShape` marking every optional field (/home/user/orkestrel/toolbox/src/core/shapers.ts:255-272, /home/user/orkestrel/toolbox/src/core/shapers.ts:508-510, /home/user/orkestrel/toolbox/guides/toolbox.md:344). Arguments stay flat and serialized: a query condition's `values` field is always an array, a key field takes one value or an array, and the fluent query form is rejected (/home/user/orkestrel/toolbox/src/core/shapers.ts:418-470, /home/user/orkestrel/toolbox/src/core/constants.ts:374, /home/user/orkestrel/toolbox/guides/toolbox.md:346). The listing advertises the one-sentence summary, and a `describe` tool built by `createDescribeTool` returns the full description on demand (/home/user/orkestrel/toolbox/src/core/constants.ts:365, /home/user/orkestrel/toolbox/src/core/factories.ts:823-840, /home/user/orkestrel/toolbox/guides/toolbox.md:342).

### How tools read and write

A store is an optional constructor option, and omitting it means no persistence (/home/user/orkestrel/toolbox/src/core/types.ts:568-571, /home/user/orkestrel/toolbox/src/core/factories.ts:1153-1157). The `create` operation refuses an id already cached or stored, refuses an unknown driver name, builds the database, awaits `store.set`, and publishes the handle to the resolver only after that write succeeds (/home/user/orkestrel/toolbox/src/core/factories.ts:1180-1221). Every other operation resolves an uncached id by rebuilding it from the store (/home/user/orkestrel/toolbox/src/core/databases/DatabaseResolver.ts:93-120). The `destroy` operation closes the cached handle, drops it from the cache, and deletes the stored definition (/home/user/orkestrel/toolbox/src/core/factories.ts:1297-1309). A `readonly` option refuses the six mutating operations from the frozen `DATABASE_TOOL_MUTATIONS` list before any resolution or storage access (/home/user/orkestrel/toolbox/src/core/factories.ts:1169-1175, /home/user/orkestrel/toolbox/src/core/constants.ts:431-438). The `records` operation clamps to a cap (default 1000), probes one extra row, and returns `{ rows, count, truncated, limit }`, and a caller's limit can only lower the cap (/home/user/orkestrel/toolbox/src/core/constants.ts:429, /home/user/orkestrel/toolbox/src/core/helpers.ts:488-493, /home/user/orkestrel/toolbox/guides/toolbox.md:350). The `timeout` option mints a fresh `AbortSignal.timeout` for seven table operations only, and the handler never reads the caller's own signal (/home/user/orkestrel/toolbox/src/core/factories.ts:1164-1177, /home/user/orkestrel/toolbox/ROADMAP.md:2).

### Refusal wording

Refusals are short and name the offending value.

- `malformed database call` for a call that fails the contract parse (/home/user/orkestrel/toolbox/src/core/factories.ts:1165-1167).
- `operation 'add' is disabled in readonly mode` for a gated write (/home/user/orkestrel/toolbox/src/core/factories.ts:1169-1174).
- `database 'ID' already exists` and `unknown driver 'NAME'`, where `NAME` stands for the requested driver key (/home/user/orkestrel/toolbox/src/core/factories.ts:1185, /home/user/orkestrel/toolbox/src/core/factories.ts:1192).

A `DatabaseError` is re-thrown as a `DATABASE` toolbox error with the upstream code in `context.code`, and the tool's own `TOOL` errors pass through unwrapped (/home/user/orkestrel/toolbox/src/core/factories.ts:1311-1323). `ToolManager.execute` flattens every failure to its message string, so code and context reach only an in-process caller (/home/user/orkestrel/toolbox/guides/toolbox.md:338, /home/user/orkestrel/toolbox/guides/toolbox.md:352). The lists of valid manager and model names ride only in context, so an MCP caller never sees them (/home/user/orkestrel/toolbox/src/core/helpers.ts:369, /home/user/orkestrel/toolbox/src/core/helpers.ts:401).

### How runs and results are recorded

Toolbox has no run directory, results file, or generated run id; runs are recorded only by injected stores (/home/user/orkestrel/toolbox/src/core/factories.ts:541, /home/user/orkestrel/toolbox/guides/toolbox.md:328). The workflow tool forwards its store to the runner, which checkpoints a snapshot keyed by the workflow id, so repeated runs of one authored name replace one snapshot, and the tool returns `{ status, count, durable?, fault? }` (/home/user/orkestrel/toolbox/src/core/helpers.ts:109, /home/user/orkestrel/toolbox/src/core/types.ts:129, /home/user/orkestrel/toolbox/tests/src/core/factories.test.ts:1115-1138). The agent tool awaits `store.set(active.snapshot())` after a successful generation under a freshly minted conversation id, and a store failure fails the tool call (/home/user/orkestrel/toolbox/src/core/factories.ts:780-785, /home/user/orkestrel/toolbox/guides/toolbox.md:332). The workspace tool's store backs only the manager's open and save, so edits persist only on an explicit save (/home/user/orkestrel/toolbox/src/core/types.ts:205-212, /home/user/orkestrel/toolbox/guides/toolbox.md:330).

## 5. The MCP and terminal surface

Toolbox contains no MCP server and no transport; handlers return plain values that appear identically over the agent loop and MCP (/home/user/orkestrel/toolbox/src/core/helpers.ts:98, /home/user/orkestrel/toolbox/guides/toolbox.md:318). Publication belongs to `@orkestrel/tool`, whose `definitions()` method an MCP bridge maps onto the protocol's tool listing while routing each invocation to `execute` (/home/user/orkestrel/toolbox/guides/tool.md:21, /home/user/orkestrel/toolbox/guides/tool.md:484). The package publishes a core entry at `.` and a server entry at `./server`, each with ECMAScript module (ESM) and CommonJS (CJS) builds (/home/user/orkestrel/toolbox/package.json:26-40).

The only network surface is the `createTerminalRoutes` function on the server entry, which returns structural `{ method, path, handler }` records: a GET route streaming server-sent events (SSE) and a POST route accepting `{ id, values }` on the default path `/terminals/:name` (/home/user/orkestrel/toolbox/src/server/factories.ts:31, /home/user/orkestrel/toolbox/src/server/constants.ts:8, /home/user/orkestrel/toolbox/guides/toolbox.md:232-234). A `x-orkestrel-token` header gate fails closed and re-validates on every 15000 ms keepalive (/home/user/orkestrel/toolbox/src/server/constants.ts:15, /home/user/orkestrel/toolbox/src/server/terminals/TerminalConnection.ts:71, /home/user/orkestrel/toolbox/src/server/terminals/TerminalConnection.ts:113). Wire failures map to Hypertext Transfer Protocol (HTTP) statuses 401, 404, 413, 400, and 422, and only a rejected answer returns a body carrying per-field errors (/home/user/orkestrel/toolbox/src/server/terminals/TerminalBridge.ts:92-136).

A terminal is a named prompt endpoint of the `TerminalManager` class in `@orkestrel/terminal`, not a shell and not a run recorder (/home/user/orkestrel/toolbox/src/core/types.ts:432, /home/user/orkestrel/toolbox/guides/toolbox.md:9). The `ask` tool poses a form to another terminal and blocks until answered, and the `answer` tool lists or answers pending forms, with the `from` and `to` identities fixed at construction so a model cannot spoof them (/home/user/orkestrel/toolbox/src/core/factories.ts:882, /home/user/orkestrel/toolbox/src/core/factories.ts:980-1010, /home/user/orkestrel/toolbox/tests/src/core/factories.test.ts:1805).

## 7. What did not work or was retired

The following gaps and retirements are recorded in toolbox, each with its stated or evident reason.

- Rows never became durable by default: only the schema persists, and a re-mint over the memory driver is empty; the reason is that the store owns config and the driver owns rows (/home/user/orkestrel/toolbox/guides/toolbox.md:360, /home/user/orkestrel/toolbox/src/core/factories.ts:1108-1111).
- The JSON driver is promised in comments but never wired or tested, so every durable path in toolbox is unproven (/home/user/orkestrel/toolbox/src/core/stores/DatabaseDefinitionStore.ts:16-22, /home/user/orkestrel/toolbox/src/core/factories.ts:1150).
- The comment calls the memory store "the default store the tools persist through", while the tool has no store unless one is passed (/home/user/orkestrel/toolbox/src/core/factories.ts:1028-1031, /home/user/orkestrel/toolbox/src/core/types.ts:568-571).
- Concurrency is unsolved: no per-id serialization, no compare-and-set, and a non-atomic check-then-set, documented as a single-writer limit instead (/home/user/orkestrel/toolbox/src/core/factories.ts:1112-1116, /home/user/orkestrel/toolbox/src/core/factories.ts:1180-1221).
- Corruption collapses into absence, and the retired `keys` definition field (replaced by `primary`) is rejected by the guard rather than migrated, so a stale entry silently disappears (/home/user/orkestrel/toolbox/src/core/validators.ts:108, /home/user/orkestrel/toolbox/tests/src/core/validators.test.ts:140-147).
- The fluent query form and earlier create-key and criteria vocabularies are retired, with tests pinning their rejection; the reason recorded is that small models chain calls and guess arity (/home/user/orkestrel/toolbox/tests/src/core/shapers.test.ts:457, /home/user/orkestrel/toolbox/tests/src/core/shapers.test.ts:524, /home/user/orkestrel/toolbox/src/core/constants.ts:374).
- The caller's cancellation signal is ignored by seven tools, and the database tool substitutes its own timeout; roadmap item 2 leaves the ruling open (/home/user/orkestrel/toolbox/ROADMAP.md:2, /home/user/orkestrel/toolbox/src/core/factories.ts:1164-1177).
- Restating an upstream handler type drifted and caused the typecheck failure behind the 0.0.14 adoption; roadmap item 1 asks to derive it (/home/user/orkestrel/toolbox/ROADMAP.md:1, /home/user/orkestrel/toolbox/src/core/types.ts:670).
- Structured error detail is lost to a remote model because `ToolManager.execute` flattens failures to message text (/home/user/orkestrel/toolbox/guides/toolbox.md:352).
- Each store-taking tool picked a different failure semantic (data on the result for workflow, a throw for agent, explicit save for workspace), which the guide documents as deliberate divergence (/home/user/orkestrel/toolbox/guides/toolbox.md:328-332).
- The relation tool has no readonly gate, so its link and unlink writes are ungated (/home/user/orkestrel/toolbox/guides/toolbox.md:354).
- The endpoint tool coerces scalars and silently drops unknown keys by default, so a call can reach the handler altered (/home/user/orkestrel/toolbox/src/core/factories.ts:1662-1675, /home/user/orkestrel/toolbox/tests/src/core/factories.test.ts:4351).
- Test titles drifted behind the code (column field names, error-code counts, a contract 0.0.6 pin), and roadmap item 3 admits the parity gate does not reach a test bullet's prose (/home/user/orkestrel/toolbox/tests/src/core/shapers.test.ts:502, /home/user/orkestrel/toolbox/tests/src/core/factories.test.ts:3680, /home/user/orkestrel/toolbox/ROADMAP.md:3).

## 8. Implications for a journey store in @orkestrel/browser

Each recommendation follows from a finding in the preceding sections.

1. Lay the store out as one file per entry under `tmp/browsers`: `tmp/browsers/journeys/JOURNEY_ID.json` for a recorded journey and `tmp/browsers/runs/RUN_ID/run.json` for a run, where `JOURNEY_ID` and `RUN_ID` are validated slug ids and binary captures sit beside `run.json` in the run folder. One file per entry keeps a write scoped to one journey, unlike the one-file-per-driver JSON driver that rewrites every table (section 2, the JSON store).
2. Give every journey file an integer `revision` field and a `format` version field. Make `set` take an expected revision and refuse a mismatch, because toolbox has no revision anywhere and cannot detect a lost update (section 2, revisions).
3. Mint each run id at the producer, never from the journey name, because the workflow tool's name-keyed snapshot makes reruns overwrite while the agent tool's minted ids accumulate cleanly (section 4, runs).
4. Write through a sibling temporary file and `rename` in the same directory, the pattern the JSON driver documents, and serialize writes per id inside the store, because toolbox left both atomicity and concurrency to an untested driver and a documented single-writer limit (section 2).
5. Resolve every id to a path and refuse any path outside `tmp/browsers`, because neither toolbox nor the JSON driver mirror describes a containment check (section 2, the JSON store).
6. Narrow every read through a total guard, resolve `undefined` only for an absent file, and refuse a corrupt or old-format file with a typed error naming the id and the path; add a migrate-or-refuse step keyed on `format`. Toolbox's collapse of corruption into absence made retired `keys` entries vanish silently (section 7).
7. Put `list({ limit, offset })` on the store interface itself, returning `{ entries, count, truncated, limit }` with a configured cap that a caller can only lower and a one-extra-entry probe, and sort by id for stable pages. Report unreadable files in a separate `faults` array so one bad file never blocks a page (sections 2 and 4).
8. Expose one `journey` tool discriminated by `operation`, with flat step records (an action, a target, a value), parameters derived from one compiled contract shape, strict parsing with no coercion, a one-sentence summary, and the full protocol behind `describe` (sections 4 and 7, endpoint coercion).
9. Word every refusal so the message alone carries the fix, including the offending value and the allowed alternatives, for example `unknown journey 'checkout-guest'; stored journeys: checkout-member, signup`, because MCP callers see only the message (section 4, refusal wording).
10. Gate every write operation behind a `readonly` option over one frozen mutation list checked before any file access, and cover every write-capable tool, unlike the ungated relation tool (sections 4 and 7).
11. Persist before publish, and let a persistence failure fail the tool call, as the agent tool does; state this one rule in the guide and pin it with a failing-store test (sections 4 and 7).
12. Require the `store` option on the tool factory, with no silent default, and state that rule in one place in the guide, because toolbox's "default store" wording contradicts its no-store behavior (section 7).
13. Take the tool context and forward `context.signal` into every store call and replay step from the first release, because toolbox's ignored signal is an open roadmap item (section 7).
14. Keep live browser, page, and Chrome DevTools Protocol (CDP) session handles, and binary captures such as screenshots and traces, out of the JSON files; store a relative path to each capture, because toolbox stores only a JSON-pure blueprint and its column DSL has no blob type (sections 2 and 3).
15. Keep `@orkestrel/database` out of the browser package: build the store as a point-access interface with a memory twin and a file twin, and leave a database-backed twin to a host. Toolbox never exercised the JSON driver, its queries scan without indexes on file and memory drivers, and its nested-data limits fit journey step lists poorly (section 3).
16. Test with one conformance suite run against both twins, a fixture carrying every optional field, corruption and truncated files written straight to disk, a durability test that reopens the same path, and a paging pressure test (section 6).
